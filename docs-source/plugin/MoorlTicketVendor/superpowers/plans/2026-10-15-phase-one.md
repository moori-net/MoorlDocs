# Ticket Vendor Phase 1 Implementation Plan

Historical implementation record. The subsequent Foundation integrations and native required version defaults supersede the original field-group and nullable-version decisions below; see `docs/schema.md` for the current model and migration sequence.

**Goal:** Implement the persistence model specified in [CODEX.md](../../../CODEX.md).
**Architecture:** Native Shopware DAL definitions, typed entities and collections; reuse Foundation's ID field collection and lifecycle helper. One non-destructive migration creates eight tables. Translation definitions use the generated Core parent FKs for compatibility with its translation resolver.
**Tech Stack:** Installed Shopware 6.7.14.1, Doctrine DBAL, MySQL/MariaDB, PHPUnit 11.
**Spec:** `CODEX.md` in this plugin.

## Constraints and decisions

- Only schema, DAL, registration, tests and documentation; no issuing or checkout behavior.
- Existing plugin has staged user changes and no initial commit. Work in place; preserve staging and do not create commits.
- Foundation's broad field groups introduce unrelated columns. Reuse `FieldEntityCollection` for primary keys; implement the exact remaining fields with native DAL classes.
- Restrict historical FK deletion; cascade only translations. Nullable version pairs require explicit versions and SQL checks.
- Hash/ciphertext are binary values represented by BlobField, without ApiAware. No token generation or encryption.
- Ruling: Translation FKs use `moorl_tv_ticket_sale_id`/`moorl_tv_ticket_type_id`; an initial integration run proved that the Core resolver hardcodes these names. The explicit compatibility clause in CODEX.md takes precedence over the proposed short names.
- Ruling: FK updates use RESTRICT; MySQL error 3823 rejects checks on the nullable FK pairs with ON UPDATE CASCADE.
- Ruling: Test kernel enables Symfony's test container and adds a database suffix to the existing cache hash; replacing that hash hid newly activated plugin definitions.
